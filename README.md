# OR-Reg

โครงเริ่มต้นระบบทะเบียนผ่าตัด พัฒนาด้วย Next.js 16, TypeScript, Tailwind CSS 4, shadcn/ui และ Base UI, Prisma 7, MySQL และ Better Auth ใช้ pnpm เป็น package manager

**สถานะ: อยู่ระหว่างพัฒนา ยังไม่พร้อมใช้กับข้อมูลผู้ป่วยจริง** มีหน้าเข้าสู่ระบบ จัดการบัญชี ค้นหาและซิงก์ HOSxP ออกเลขทะเบียน ดู Operation และทีมผ่าตัด บันทึกเวลาและข้อมูลเพิ่มเติม รวมถึง dashboard และรายงานสรุป มีการทดสอบด้วยข้อมูลจำลอง แต่ยังไม่ได้ทดสอบกับ HOSxP ของโรงพยาบาล

## เริ่มต้นพัฒนา

1. ใช้ Node.js รุ่นที่ Next.js 16 และ Prisma 7 รองรับ และ pnpm รุ่นที่ระบุใน `package.json` แล้วติดตั้ง dependency ด้วย `pnpm install --frozen-lockfile` (ขั้นตอนนี้สร้าง Prisma Client ด้วย)
2. คัดลอก `.env.example` เป็น `.env` และตั้งค่า `DATABASE_URL`, `BETTER_AUTH_SECRET` และ `BETTER_AUTH_URL` สำหรับเครื่องพัฒนา โดย secret ต้องสุ่มและเก็บเป็นความลับ
3. สร้างฐานข้อมูล MySQL **แยกสำหรับแอป** ชื่อ `orreg_aranhos` แล้วรัน `pnpm exec prisma migrate deploy` เพื่อสร้างตารางในแอป
4. รัน `pnpm dev` และเปิด `http://localhost:50004` (ใช้พอร์ตเดียวกันสำหรับ `pnpm start`)

บน Windows สร้าง superadmin คนแรกด้วย `pnpm.cmd setup:superadmin` แล้วกรอกชื่อ อีเมล และรหัสผ่านตามที่โปรแกรมถาม สคริปต์ใช้ฐานข้อมูลจาก `.env.development` และไม่แสดงรหัสผ่านขณะพิมพ์ จากนั้นเข้าสู่ระบบที่ `http://localhost:50004/auth/signin` สคริปต์ทำงานได้เมื่อยังไม่มีบัญชีเท่านั้น รหัสผ่านต้องยาว 6–128 ตัวอักษร โดยไม่มีข้อกำหนดชนิดตัวอักษร

หากต้องการใช้คำสั่งแบบไม่โต้ตอบ ตั้งค่า `BOOTSTRAP_EMAIL`, `BOOTSTRAP_NAME`, `BOOTSTRAP_PASSWORD` และ `DATABASE_URL` ใน environment แล้วรัน `pnpm bootstrap:superadmin` เก็บค่า environment เป็นความลับและลบออกเมื่อดำเนินการเสร็จ สคริปต์ใช้ Node.js ที่รองรับการรัน TypeScript โดยตรง (ทดสอบด้วย Node.js 24)

การสมัครบัญชีสาธารณะถูกปิดไว้ บัญชีใหม่มีบทบาทเริ่มต้นเป็น `USER`; `SUPERADMIN` เข้าถึงทุกส่วน, `ADMIN` จัดการบัญชี, `NURSE` อ่านและแก้ไขทะเบียน, `DOCTOR` ดู dashboard และอ่านทะเบียน, และ `USER` ดู dashboard เท่านั้น ทุกบทบาทดู dashboard ได้ เฉพาะ superadmin จัดการบัญชี superadmin ได้ ระบบป้องกันการระงับหรือลดสิทธิ์ superadmin ที่ใช้งานอยู่คนสุดท้าย และเก็บประวัติการจัดการบัญชีโดยไม่เก็บรหัสผ่าน

หน้าจัดการบัญชีรองรับการค้นหา กรอง เรียง และแบ่งหน้า ข้อมูลองค์กร ภารกิจ กลุ่มงาน ตำแหน่ง และระดับตำแหน่งเป็นข้อความอิสระที่ไม่บังคับ การลบบัญชีเป็นการซ่อนและปิดบัญชีพร้อมยกเลิก session โดยคงทะเบียนและประวัติเดิมไว้ อีเมล ชื่อผู้ใช้และข้อมูลจับคู่ Provider ID ยังคงสงวนกับบัญชีเดิม เลือกตัวกรองบัญชีที่ลบเพื่อกู้คืนได้ โดยบัญชีที่กู้คืนจะยังถูกระงับจนกว่าผู้ดูแลเปิดใช้งานอีกครั้ง ไม่สามารถลบบัญชีตนเองหรือ superadmin ที่ใช้งานอยู่คนสุดท้าย

หน้าโปรไฟล์ให้เจ้าของแก้ชื่อ ข้อมูลหน่วยงาน และตำแหน่งได้เอง การเปลี่ยนรหัสผ่านต้องยืนยันรหัสเดิม และปิด session อื่นเมื่อสำเร็จ หากยืนยันผิดหลายครั้งระบบพักการเปลี่ยนรหัสชั่วคราว บัญชีที่ไม่มีรหัสผ่านต้องติดต่อผู้ดูแลเพื่อกำหนดรหัสผ่าน

ทุกบัญชีที่ใช้งานได้มีหน้า `/profile` สำหรับเพิ่มรูปโปรไฟล์และลายเซ็นของตนเอง ลายเซ็นเขียนด้วยเมาส์ ปากกา หรือสัมผัส หรืออัปโหลดภาพ PNG/JPG/WebP ได้ ภาพต้นฉบับต้องไม่เกิน 3 MB ระบบตรวจและแปลงภาพก่อนจัดเก็บในฐานข้อมูลแอป มีลายเซ็นปัจจุบันเพียงหนึ่งรายการต่อบัญชี การบันทึกใหม่จะแทนรายการเดิม รูปและลายเซ็นเข้าถึงได้เฉพาะเจ้าของบัญชี การแก้ไขบันทึก audit ใน transaction เดียวกัน และการดูภาพลายเซ็นมี audit โดยไม่เก็บภาพลงใน audit log ลายเซ็นยังไม่ได้ถูกนำไปลงนามในรายงานหรือเอกสารอัตโนมัติ

## มาตรฐานไลบรารี

อ่านตัวแปร environment ของแอปผ่าน `lib/env.ts` และของคำสั่ง Prisma/bootstrap ผ่าน `lib/cli-env.ts` ซึ่งตรวจค่าด้วย `@t3-oss/env-nextjs` และ Zod โดย ESLint ป้องกันการอ่าน `process.env` ตรงจากโค้ดแอปและสคริปต์ ส่วน `instrumentation.ts` ตรวจ `NEXT_RUNTIME` ของ Next.js ผ่าน T3 Env และใช้รูปแบบที่ Next.js กำหนดเพื่อแยก Node.js จาก Edge ตัวแปรสำหรับ HOSxP, Provider ID และ SMTP เป็นตัวเลือก แต่จะต้องตั้งค่าให้ครบเมื่อใช้บริการนั้น

ใช้ TanStack Query สำหรับคำขอข้อมูลใน client, TanStack Table สำหรับตาราง, React Hook Form ร่วมกับ Zod สำหรับฟอร์ม, Zustand สำหรับสถานะหน้าจอ, Recharts สำหรับกราฟ และ Sonner สำหรับข้อความแจ้งผล คำขอที่มีข้อมูลผู้ป่วยไม่เก็บ cache ถาวร และล้าง query cache เมื่อออกจากระบบ

หน้าจอและการโหลดข้อมูลของแต่ละงานอยู่ใน `features/<งาน>/pages` ส่วนคอมโพเนนต์และ skeleton อยู่ใน `features/<งาน>/components` โดย route มีเฉพาะการเชื่อมหน้าจอและไฟล์ loading ตารางที่กว้างรองรับการเลื่อนด้วยการสัมผัสและคีย์บอร์ด

## เข้าสู่ระบบและกู้รหัสผ่าน

`/signin` ใช้ Provider ID ส่วน `/auth/signin` รองรับ Provider ID และชื่อผู้ใช้หรืออีเมลพร้อมรหัสผ่าน ผู้ดูแลสร้างบัญชีและกำหนดชื่อผู้ใช้และเลขประจำตัวประชาชนที่ถูกต้องในหน้าจัดการบัญชี เลขประจำตัวเก็บเฉพาะ SHA-256 เพื่อจับคู่กับ `hash_cid` ที่ได้จาก Provider ID ไม่สร้างบัญชีอัตโนมัติ และบัญชีที่ถูกระงับเข้าสู่ระบบไม่ได้ เมื่อต้องการเปลี่ยนเลขประจำตัวให้กรอกเลขใหม่ในหน้าจัดการบัญชี ระบบจะยกเลิกการผูก Provider ID และเซสชันเก่าของบัญชีนั้น

ตั้งค่า `MOPH_HEALTH_ID_BASE_URL`, `MOPH_HEALTH_ID_CLIENT_ID`, `MOPH_HEALTH_ID_CLIENT_SECRET`, `MOPH_PROVIDER_ID_BASE_URL`, `MOPH_PROVIDER_ID_CLIENT_ID` และ `MOPH_PROVIDER_ID_CLIENT_SECRET` ใน environment ของเครื่อง รวมทั้งลงทะเบียน callback `${BETTER_AUTH_URL}/api/auth/callback/moph-provider-id` กับ Health ID ให้ตรงกับสภาพแวดล้อมที่ใช้ ต้องทดสอบกับบริการจริงและบัญชีที่ได้รับอนุญาตก่อนเปิดใช้งาน

การลืมรหัสผ่านต้องตั้งค่า `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD` และ `SMTP_FROM` ใน environment ของเครื่อง (พอร์ต 465 ใช้ TLS โดยตรง ส่วนพอร์ตอื่นใช้ STARTTLS) ตั้ง `BETTER_AUTH_URL` เป็น URL ที่ผู้รับเข้าถึงได้ ลิงก์มีอายุหนึ่งชั่วโมงและการตั้งรหัสผ่านใหม่จะยกเลิกเซสชันเดิม ห้าม commit รหัสผ่าน SMTP ลง repository ตรวจสอบการส่งอีเมลจริงกับ SMTP ของโรงพยาบาลก่อนใช้งาน

## Audit log

ระบบบันทึกเหตุการณ์ตั้งแต่ติดตั้ง migration เป็นต้นไปในตาราง `AuditLog` ของฐานข้อมูลแอป และเฉพาะ `SUPERADMIN` ดูได้ที่ `/admin/audit` มีการบันทึกการเริ่มเซสชัน การเข้าสู่ระบบไม่สำเร็จ การออกจากระบบ การกู้รหัสผ่าน การจัดการบัญชี การเปิดดูข้อมูลผ่าตัด การซิงก์ และการแก้ไขทะเบียน รวมถึงการปฏิเสธสิทธิ์ที่จุดเหล่านี้ การเปลี่ยนแปลงบัญชีและทะเบียนบันทึก audit ใน transaction เดียวกัน ส่วนประวัติก่อน–หลังที่มีอยู่เดิมยังเก็บแยกในตารางประวัติเดิม

Audit กลางเก็บรหัสผู้ดำเนินการ รหัสอ้างอิง ผล เวลา และข้อมูลประกอบที่อนุญาตเท่านั้น ไม่บันทึกรหัสผ่าน โทเคน CID ชื่อผู้ป่วย HN หรือ request body การเข้าสู่ระบบที่ไม่สำเร็จไม่บันทึกตัวระบุที่ผู้ใช้กรอก ตารางนี้ไม่มีหน้าลบหรือแก้ไขผ่านแอป แต่ผู้มีสิทธิ์ฐานข้อมูลระดับสูงยังแก้ไขได้ จึงต้องจำกัดสิทธิ์ฐานข้อมูล สำรองข้อมูล และกำหนดระยะเวลาเก็บรักษาตามนโยบายโรงพยาบาล

ระบบลบเฉพาะแถวใน `AuditLog` ที่เก่ากว่า 30 วันโดยอัตโนมัติเมื่อตัวเซิร์ฟเวอร์ Node.js เริ่มทำงานและตรวจซ้ำทุก 10 นาที ข้อมูลที่ถูกลบจะกู้คืนได้เฉพาะจากข้อมูลสำรองตามนโยบายของโรงพยาบาล ตารางประวัติการแก้ไขทะเบียนและการจัดการบัญชีที่เก็บแยกไม่ถูกลบด้วย หากเซิร์ฟเวอร์หยุดทำงาน ระบบจะลบข้อมูลที่ครบกำหนดเมื่อเริ่มต้นอีกครั้ง ส่วนระบบที่หยุดเซิร์ฟเวอร์อัตโนมัติหรือใช้ serverless ต้องจัดตารางงานภายนอกหากต้องการรับประกันเวลาการลบ

เหตุการณ์ Better Auth บางอย่าง เช่น การตั้งรหัสผ่านใหม่และออกจากระบบ บันทึกหลังจาก Better Auth ทำรายการแล้ว หากฐานข้อมูลล่มระหว่างขั้นตอนดังกล่าว การดำเนินการอาจสำเร็จโดยบันทึก audit ไม่สำเร็จ ต้องติดตามข้อผิดพลาดของระบบและจัดกระบวนการตรวจสอบเพิ่มเติมก่อนใช้งานจริง

Prisma adapter ในโครงเริ่มต้นนี้อ่าน host, port, username, password และชื่อฐานข้อมูลจาก `DATABASE_URL` เท่านั้น ยังไม่ได้ตั้งค่า TLS หรือ connection options จาก URL จึงต้องเพิ่มและทดสอบการเชื่อมต่อที่เหมาะสมกับสภาพแวดล้อมก่อนใช้งานจริง

## HOSxP

`lib/hosxp/operations.ts` เตรียมคำสั่งอ่านรายการตามวันที่และทีมผ่าตัดจาก SQL ที่โรงพยาบาลให้มา โดยใช้ parameter และ transaction แบบ read-only ข้อมูลรวมถึงข้อมูลระบุตัวผู้ป่วยและข้อมูลทางการเงิน API `/api/hosxp/operations?date=YYYY-MM-DD` และ `/api/hosxp/operations/{operationId}/team` ตรวจสิทธิ์ `register:read` ฝั่งเซิร์ฟเวอร์และไม่ cache ผลลัพธ์ ต้องทดสอบกับบัญชีและฐานข้อมูลจริงก่อนนำไปใช้งาน

โค้ดเดียวกันอ่าน `operation_position` และจับคู่ `position_id` กับกลุ่มบุคลากรตามที่แจ้ง: กลุ่ม 1 = 1, กลุ่ม 2 = 5, กลุ่ม 3 = 2, กลุ่ม 4 = 3 และกลุ่ม 5 = 4, 6, 7, 8 โดยชื่อแสดงจาก HOSxP ตำแหน่งที่ไม่อยู่ในชุดนี้จะถูกส่งกลับโดยไม่กำหนดกลุ่มเพื่อให้ตรวจสอบเพิ่มเติม

เมื่อผู้มีสิทธิ์ซิงก์ ระบบดึงรายการจาก HOSxP ตาม `request_operation_date` แล้วจัดเลขให้รายการใหม่ใน transaction เดียว โดยบังคับไม่ให้เลขลำดับซ้ำภายในปีงบประมาณและเดือนเดียวกัน และไม่ให้ HOSxP operation เดียวกันมีทะเบียนซ้ำ เลขแสดงเป็น `ลำดับ/เดือน` ปีงบประมาณเริ่ม 1 ตุลาคม และลำดับเริ่มใหม่ทุกเดือน หาก HOSxP เปลี่ยนวันผ่าตัด ต้องค้นหาและซิงก์วันที่ใหม่: เมื่อเปลี่ยนข้ามเดือนระบบออกเลขใหม่ตามเดือนใหม่ เมื่อเปลี่ยนภายในเดือนเดียวกันระบบคงเลขเดิม ระบบเก็บประวัติก่อน–หลังและไม่ใช้เลขเก่าซ้ำ ข้อมูลเพิ่มเติมและเวลาที่เคยบันทึกยังคงอยู่ เจ้าหน้าที่ควรตรวจสอบเวลาเดิมเมื่อวันผ่าตัดเปลี่ยน

เวลาในทะเบียนมีสี่จุด ได้แก่ เข้าห้องผ่าตัด เริ่มผ่าตัด สิ้นสุดผ่าตัด และออกจากห้องผ่าตัด หน้าจอใช้เวลาประเทศไทย รองรับการผ่าตัดข้ามวัน ตรวจลำดับเวลา และป้องกันการเขียนทับเมื่อมีผู้แก้ไขพร้อมกัน ประวัติก่อน–หลังบันทึกในฐานข้อมูลแอปเท่านั้น ไม่มีการบันทึกกลับ HOSxP

Patho, Pre-op และ Post-op เป็น checkbox ชนิดการดมยาเลือกได้จาก LA, TIVA, SB, NB, LMA, GA และ GA_WITH_MASK ความเร่งด่วนเลือก ELECTIVE หรือ EMERGENCY โดยนำค่า `emergency_name` ที่ตรงกันจาก HOSxP มาเป็นค่าเริ่มต้นตอนซิงก์ ประเภทผ่าตัดเลือกผ่าตัดใหญ่หรือผ่าตัดเล็ก และกรณีผ่าตัดเล็กเลือกช่วงเวลาในหรือนอกเวลาราชการได้ ผู้ใช้เป็นผู้เลือกช่วงเวลาเอง ไม่ได้คำนวณอัตโนมัติจากเวลาผ่าตัด ข้อมูลเหล่านี้เว้นว่างได้และการแก้ไขถูกเก็บประวัติก่อน–หลัง Operation และบุคลากรดึงจาก HOSxP เพื่อแสดงอย่างเดียว รายงานสรุปแยกเดือน ประเภทผ่าตัด ช่วงเวลาผ่าตัดเล็ก ความเร่งด่วน ชนิดการดมยา และจำนวน checkbox พร้อมดาวน์โหลด CSV หรือ PDF ที่ฝังฟอนต์ Sarabun สำหรับภาษาไทย

ตั้งค่า `HOSXP_*` ตาม `.env.example` ด้วยบัญชีแยกที่ได้รับสิทธิ์ `SELECT` เฉพาะตารางที่ต้องอ่านเท่านั้น สิทธิ์ read-only ต้องบังคับที่ฐานข้อมูลด้วย ห้ามใช้บัญชีแอปหรือบัญชีที่เขียน HOSxP ได้ การเชื่อมต่อ HOSxP ใช้ TCP โดยไม่เข้ารหัส TLS ในทุก environment ดังนั้นให้จำกัดการเชื่อมต่อไว้ในเครือข่ายโรงพยาบาลที่เชื่อถือได้

## ข้อมูลที่ต้องกำหนดก่อนพัฒนาต่อ

- ตรวจสอบ SQL และโครงสร้าง HOSxP กับฐานข้อมูลจริง รวมถึงบัญชีฐานข้อมูลแยกที่มีสิทธิ์อ่านอย่างเดียว ห้ามนำ `DATABASE_URL` สำหรับ migration ไปชี้ที่ HOSxP
- กติกาทะเบียนเมื่อรายการถูกยกเลิกใน HOSxP
- รายงานเฉพาะเพิ่มเติมที่โรงพยาบาลต้องการ และการตรวจสอบข้อมูลกับ HOSxP จริง
